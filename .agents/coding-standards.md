# 代码规范

## 修改原则

- 先通过代码、测试、日志或可复现步骤定位事实与根因，再修改代码；不得靠猜测修复。
- 只修改需求直接相关的代码，不顺手格式化、重命名或重构无关区域。
- 理解上下文可以阅读历史代码，但只有需求涉及或修复其缺陷时才修改历史代码。
- 保留工作区中用户已有的未提交改动；发现重叠修改时先理解并在其基础上工作。

## 实现质量

- 使用表达业务语义的函数、变量、类型和常量名，名称必须与实际用途一致。
- 业务状态、操作类型、存储键、阈值和通道名使用具名常量或枚举，不散落魔法字符串或魔法数字。
- 访问对象成员、数组元素和接口返回值前处理 `null`/`undefined`；优先使用可选链、空值合并和明确默认值。
- 异步流程必须处理成功、失败和清理路径；订阅、计时器与事件监听在组件卸载或任务结束时释放。
- 不吞掉会影响用户判断的异常；转换为稳定的 `{ success, error }` 等现有返回模型，并保留可操作的错误信息。
- 批量操作逐项返回结果，单项失败不得无故阻断其余项目；需要整体中止的场景必须有明确业务依据。
- 可能阻塞 Electron 主线程或渲染线程的文件、Git、网络和子进程操作使用异步 API，并提供统一 loading 状态。

## 注释

- 新增或修改的函数、方法必须说明用途；关键参数和返回值不直观时一并说明。
- 新增或修改的业务变量必须说明存储的数据；循环索引、显而易见的临时值无需机械复述代码。
- 非显而易见的分支说明其业务场景；复杂算法、兼容处理和 workaround 注释 WHY，而不是翻译代码。
- Bug 修复注释说明现象、根因及当前方案为何有效，避免只写“修复问题”。
- 注释与代码必须同步，过期注释视为缺陷。

## 格式与依赖

- 遵循现有 ESLint、Prettier 和 TypeScript 配置，不手工制造与格式化器冲突的风格。
- 新增依赖前确认现有依赖和平台 API 无法合理满足需求，并评估 Electron 打包体积、许可证和跨平台支持。
- UI 优先复用 antd 与 `@ant-design/icons`，不得为已有能力重复引入组件库或图标库。
